A. Hash Table

The hash table is the class ChainingHashTable in main.py. It uses no additional library or class; it is built only from plain lists. Its insert function takes the package ID as input and stores the delivery address, delivery deadline, delivery city, delivery zip code, package weight and delivery status (which carries the delivery time once the package is delivered). The routing details that are not part of the table (notes, assigned truck, departure and delivery times) are kept outside it, in the program’s PackageRecord objects.

B. Look-Up Function

The lookup(package_id) method of ChainingHashTable takes a package ID and returns each of the data components listed in part A: address, deadline, city, zip code, weight and status (including the delivery time). Menu option 2 of the interface first refreshes the stored status for the time the user entered and then calls it. A screenshot appears in Figure E2.

C. Original Program

The program is in the file main.py. Its first line is the identifying comment containing the student ID, and detailed comments explain both the process (what each class and function does) and the flow of the program (load data → load trucks → route each truck → user interface). The command-line interface lets the user (1) view the status of all packages, grouped by truck, at any time of day, (2) look up a single package at any time, and (3) view the mileage of every truck and the total mileage. Each status line reports the package as Delayed, At Hub, En Route or Delivered at HH:MM:SS, so the delivery time is always shown.

F. Justification of the Package Delivery Algorithm

The solution uses the Nearest Neighbor algorithm, a greedy heuristic for the Traveling Salesman Problem. Each truck starts at the hub with its loaded packages and repeatedly drives to the closest address among its undelivered packages until none remain (Cormen et al., 2009; Rosenkrantz et al., 1977).

F1. Strengths of the algorithm

  1. Efficient and simple. Each truck holds at most 16 packages, and the algorithm compares the truck's position with every remaining package once per stop. It runs in O(N2) time and O(1) extra space, so the whole route set is produced instantly. The simple logic is also easy to read, test and debug.
  2. Produces a short route. The three trucks drove 113.0 miles in total, which is well under the 140-mile limit, even though the algorithm does not search for the guaranteed shortest tour.
  3. Adapts to the truck's actual position. No route is pre-planned. After every delivery the next stop is chosen from where the truck is now, so the result stays correct whichever packages are loaded. Changing a truck's load only requires changing its list of package IDs.

F3. Two other algorithms that would meet all requirements

1. Held–Karp dynamic programming. Because each truck carries at most 16 packages, the exact Held–Karp algorithm is feasible. It computes the shortest tour through all of a truck's stops by solving the problem for every subset of stops and extending the best partial tours (Held & Karp, 1962).

2. 2-opt local search. 2-opt starts from any complete route and repeatedly removes two edges and reconnects the route in the other way, keeping the change whenever it shortens the route, until no swap improves it (Croes, 1958).

F3a. How each differs from Nearest Neighbor

  • Held–Karp is exact and considers all orderings through its table of subsets, so it always finds the shortest route for a truck. Nearest Neighbor commits to one nearest stop at a time and never reconsiders. The price is O(n22n) time and O(n2n) memory compared with O(n2) time and O(1) memory.
  • 2-opt is an improvement method, not a construction method. It needs a finished route first and then changes it by reversing segments, whereas Nearest Neighbor builds a route one stop at a time and never modifies a stop once it is chosen.

G. What I Would Do Differently

If I did this project again I would change the following:

  1. Load the trucks with code instead of by hand. I assigned the packages to trucks manually after reading the special notes. I would write a loading step that first places the constrained packages (truck-2-only, grouped, delayed) and then fills the remaining space by grouping packages with nearby zip codes, so a new data set would not need manual planning.
  2. Look up distances faster. get_distance calls list.index on the address list, which scans the list each time. I would build an address-to-index table using my own hash table once, making each distance look-up O(1).
  3. Make the driver rule explicit. Truck 3's departure time is set by hand to 10:20. I would have the program compute it as the later of 10:20 and the return time of the first driver to come back.
  4. Add automated tests. I would add tests that check every deadline, special note and the 140-mile limit, instead of checking these with ad-hoc scripts.

H. Verification of the Data Structure

The chaining hash table meets every requirement in the scenario:

  • Stores every required component. Each entry is keyed by package ID and holds the address, deadline, city, zip code, weight and status for the package.
  • Fast access. The router, the Package 9 correction and the interface all find a package by its ID. A look-up or insertion is O(1) on average, and the table needs O(N) space for N packages.
  • Handles collisions and growth. Packages whose IDs hash to the same bucket are chained in that bucket's list, so no package is lost or overwritten, and the table works for more than 40 packages (Cormen et al., 2009).
  • No additional libraries or classes are used for the table itself.

H1. Two other data structures that could meet the requirements

1. Binary search tree (BST). Each node would hold a package ID and its data, with smaller IDs in the left subtree and larger IDs in the right subtree (Cormen et al., 2009).

2. Sorted array (list) with binary search. The packages would be stored in a list ordered by package ID, and each look-up would binary search the list (Cormen et al., 2009).

H1a. How each differs from the hash table

  • BST: It places data by comparing keys rather than by calculating a bucket from the key, so look-up is O(log N) on average (O(N) if the tree becomes unbalanced) rather than O(1). In return, a BST keeps the packages in sorted order, which a hash table does not.
  • Sorted array: It stores records contiguously in key order instead of in buckets. Look-up is O(log N), and an insertion must shift elements to keep the order, costing O(N), whereas a hash table insertion is O(1) on average.
